# Whole-book transcription

Checked against current official documentation on **2026-09-06**. This is documentation research, not an accuracy benchmark. No audiobook was uploaded, no paid request was made, and no model was installed. File measurements below were supplied by the source-inspection work in this session.

**Yes: Rev AI documents support for both complete original MP3s in one asynchronous job per book.** Its limit is 17 hours and 2 GB for a direct multipart upload. It provides timed words and a retrievable job ID. This is the simplest supported first experiment for the user's immediate goal: transcribe the collection, find its author-defined stories, select one, and start working with it. This recommendation is about a suitable input/output contract and low implementation effort; it does not claim Rev has the best recognition accuracy. [Rev limits](https://docs.rev.ai/faq), [Rev getting started](https://docs.rev.ai/api/asynchronous/get-started).

## What a Rev first implementation needs

Use **machine transcription**, not the human-transcription option. Official documentation maps `transcriber: "machine"` to Reverb ASR; the public selector is not an immutable dated model snapshot. Store the selected engine, full request configuration, submission time, source hash and returned provider metadata so model drift is visible. A separately priced Reverb turbo exists, but the standard Reverb path is the documented selector verified for this first implementation. [Transcriber selection](https://docs.rev.ai/api/asynchronous/transcribers), [pricing](https://www.rev.ai/pricing).

Submit through `POST https://api.rev.ai/speechtotext/v1/jobs`. Persist the returned `id` immediately. `GET /jobs/{id}` reports status; once `transcribed`, `GET /jobs/{id}/transcript` with `Accept: application/vnd.rev.transcript.v1.0+json` returns `monologues[].elements[]`. Text elements have `value`, `ts`, `end_ts`, and `confidence`; punctuation elements do not necessarily have times. Normalization should preserve this distinction. The provider's internal segments do not have to become animator's story boundaries. [Getting started and JSON example](https://docs.rev.ai/api/asynchronous/get-started).

For this local CLI, bounded polling of an existing job ID is a reasonable implementation decision; Rev recommends webhooks for a production server. Its `notification_config` webhook reports either success or failure and includes `duration_seconds` on successful jobs. Rev retries unsuccessful webhook delivery every 30 minutes for up to 24 hours. Completed jobs normally remain available for 30 days unless the account has a shorter deletion period. These allow recovery after our process restarts; they do not establish resumable file uploads or idempotent job submission. [Webhook behavior](https://docs.rev.ai/api/asynchronous/webhooks), [job retention](https://docs.rev.ai/faq).

A lost HTTP response while submitting is different from a failed job: the provider may already be working and charging. The implementation should record that ambiguous state and reconcile before automatically resubmitting the whole book. No documented idempotency key was established in this research. Rev acknowledges job-processing timeouts, but the exact numeric limits were not published in the checked FAQ; its advertised normal turnaround is not an SLA or a measured result on these files. [Rev FAQ](https://docs.rev.ai/faq).

## Coverage and boundary checks

The following are proposed engineering checks, not provider guarantees or claims of measured accuracy:

1. Preserve the original MP3 and its source hash. Do not replace the movie soundtrack with the transcription input or synthesized speech.
2. Require a completed provider job and save its raw result before normalization. Compare reported duration with the local probe and retain the difference.
3. Validate finite word times, `0 <= start <= end`, ordering, and source-duration bounds. Preserve missing timestamps as an explicit issue rather than inventing precise ones.
4. Check speech coverage across the entire recording. A last timestamp near the end cannot prove the middle is complete. Long unexplained gaps, repeated phrases, or empty regions overlapping independently detected speech need review or targeted retranscription. Silence and music are legitimate gaps, so word coverage should not be divided by total recording time as a success percentage.
5. Find author-defined stories using the transcript and audible introductions. Opening credits, a contents recital, or a title mentioned within another story can resemble a story boundary. Preserve supporting word IDs and source-relative times for each proposed story.
6. For the selected first story, inspect short audio excerpts around its proposed start and end and make a playable cut. Fine decisions about titles, music and trailing silence can follow once that story is usable.

If a different provider is selected later, technical transport chunks belong inside transcription and retain their source offsets. They must not be treated as short stories. Overlap and reconcile words at joins, retain raw chunk results, and retry only failed chunks. That can still present one book-level operation to the user, but it is more implementation work than Rev's supported whole-file job.

## Local option

`faster-whisper` can transcribe a local MP3 with segment and optional word timestamps, batched inference, and optional VAD. Its official repository demonstrates `large-v3`/`distil-large-v3` use. `WhisperX` adds phoneme alignment, but documents that some words cannot be aligned and overlapping speech remains difficult. These are useful if we later need local processing or to refine selected boundaries. Neither checked repository publishes a service-style hard maximum for a whole audiobook; practical limits depend on decoding memory, hardware, and our own resumable orchestration. No runtime or accuracy was measured on this computer, so “free” means no provider fee, not zero compute or setup cost. [faster-whisper](https://github.com/SYSTRAN/faster-whisper), [WhisperX](https://github.com/m-bain/whisperX).

## Decision ready for alignment

Recommend **Rev Reverb whole-book timed transcription first**, then story discovery, then extraction from the original audio. Implement one concrete provider and a small validated transcript artifact; a generic provider framework is unnecessary for the first milestone. The choice still requiring the user's input is whether to proceed with that complete-book experiment or first compare current models on a few representative boundary clips. Either path should report coverage and boundary evidence before treating the output as trusted.
